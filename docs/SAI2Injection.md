# SAI2 注入路线：图层识别（路线 C）

本文档记录"逆向注入"方案的设计、实测结果与使用方法。
它是 [SAI2Integration.md](SAI2Integration.md)（伴随宿主 + 剪贴板桥，路线 B）的**补充**，
两条路线并存：剪贴板桥负责"像素进出"，注入代理负责"状态识别"。

> **背景**：实测确认 SAI2 无任何官方插件接口（见 SAI2Integration.md 第一节）。
> 要在程序层面拿到"图层面板里有什么"，只能进入 SAI2 进程内部观察。
> 本方案是**只读观察**：不改 SAI2 的任何数据、不篡改任何 API 参数与返回值。

---

## 一、总体架构

```
┌────────────────────┐  CreateRemoteThread   ┌──────────────────────────────────┐
│ sai2_injector.exe  │ ──── LoadLibraryW ───► │ sai2.exe (SAI2)                  │
│  注入/弹出/查询 CLI │                        │   └─ sai2_agent.dll（已注入）     │
└─────────┬──────────┘                        │      ├─ IAT 钩子（只读观察）      │
          │                                   │      │  ExtTextOutW / DrawTextW  │
          │                                   │      │  SetDIBitsToDevice / BitBlt│
          │  命名管道 \\.\pipe\sai2agent       │      ├─ 文字↔位块配对 → 行重建     │
          │  （单行 JSON 进/出）               │      └─ 同步命名管道服务           │
┌─────────▼──────────┐                        └──────────────────────────────────┘
│ sai2_bridge.exe    │  图层面板：列表/刷新/「选中并抓取该图层」
│ sai2_agent_ctl CLI │
└────────────────────┘
```

## 二、为什么选 IAT 钩子（而不是内存结构解析 / 函数序言跳板）

| 方案 | 问题 |
| --- | --- |
| 硬编码内存偏移（解析 SAI2 内部对象） | 每个版本都要重新逆向；结构一变就崩 |
| 函数序言跳板（trampoline，MinHook 式） | 需要指令长度解码、直接改代码字节，出错面大 |
| **IAT 钩子（本方案）** | 只改导入表里的函数指针（8 字节原子写）；不碰代码；SAI2 更新大概率仍可用 |

SAI2 的导入表（实测 2023-04-05 版，x64）包含本方案所需的全部函数：
`ExtTextOutW` / `DrawTextW`（文字）、`SetDIBitsToDevice` / `BitBlt`（位块）。
主程序对这些函数的调用全部经由主模块 IAT 间接寻址，替换表项即可拦截。

## 三、SAI2 的绘制模式（实测反推）

SAI2 的 UI 不是标准 Win32 控件，而是自绘框架（窗口类 `sflRootWindow` /
`sflChildWindow` / `sflMenuWindow`）。实测绘制流水线：

1. **UI 文字画进内存表面**（内存 DC）——钩子里 `WindowFromDC` 得到 NULL、
   `GetDCOrgEx` 得到 (0,0)，文字坐标是**单元格局部坐标**；
2. **再由 SetDIBitsToDevice/BitBlt 贴到真实子窗口**——此时能拿到目标窗口与屏幕坐标；
3. 两种节奏都出现过：
   a) **逐行交错**：渲染第 i 行的文字 → 贴第 i 行；
   b) **整批**：一帧内先渲染所有行的文字（按列：先所有行的名字、再所有行的
      混合模式、再所有行的不透明度），再依次贴出行槽；
4. 图层面板：单元格 **175×55**，行距 55px；同一内容可能左右各贴一次（x=8 与 x=183）。

### 文字↔位块配对算法（AgentCore.cpp `PairPendingTexts`）

- 文字渲染（hwnd=0）进 `pendingTexts` 队列；
- 每笔面板类 blit（16≤w≤512，8≤h≤96，有屏幕坐标）到达时，消费 120ms 窗口内
  的积压文字；
- 按"**连续相同局部 y**"分列、列按局部 y 升序（名字列最先）；
  行数 = 名字列长度；第 j 行落到 `b.screenY + j*cellH`（交错模式 rows=1 →
  全部落到本笔位置）；
- 防错配三约束：120ms 时间窗；文字尺寸 ≤ blit 尺寸；**映射点必须落在目标窗口
  矩形内**（防跨窗口错配与幻影行）。

## 四、管道协议（单行 JSON）

连接 → 发一行 → 收一行 → 断开。同步 I/O（叠加 I/O 在 zig/clang windows-gnu
工具链下实测异常，见第五节）。

| 命令 | 返回 |
| --- | --- |
| `{"cmd":"ping"}` | `{"ok":true,"agent":"sai2_agent/1.0","pid":N,"hooks":{...},"log":"..."}` |
| `{"cmd":"layers"}` | `{"ok":true,"groups":[{hwnd,cls,isChild,screenRect,rows:[{y,x,screenX,screenY,tick,count,text}]}],"panelGuess":hwnd}` |
| `{"cmd":"thumbs"}` | 缩略图/位块捕获列表（含落盘 BMP 路径） |
| `{"cmd":"text.recent","n":400}` | 最近文字捕获（含未配对的原始项，诊断用） |
| `{"cmd":"reset"}` | 清空全部捕获 |
| `{"cmd":"scan.strings","substr":"图层","dump":true}` | 堆扫描（为将来内存结构逆向收集地址与 hexdump，落到 `scan_strings.txt`） |

`layers` 的 `panelGuess` 评分：行数 + 子窗口 +2 + 名字含"图层/Layer" +3 −
根窗口 5。当前实测能稳定选中图层面板。

## 五、构建与使用

```bash
bash scripts/build-zig.sh          # 第 7 步产出 sai2_agent.dll / sai2_injector.exe / sai2_fakehost.exe

# 端到端自检（不碰 SAI2；FakeHost 模拟 SAI2 的绘制方式）
./build-zig/tools/sai2_injector.exe selftest        # 实测 8/8 PASS

# 注入真 SAI2（先启动 SAI2；inject 自动找 sai2.exe，也可 --pid / --launch）
./build-zig/tools/sai2_injector.exe inject
./build-zig/tools/sai2_injector.exe layers          # 打印图层行 JSON
./build-zig/tools/sai2_injector.exe eject           # 卸载（恢复 IAT，SAI2 不受影响）
```

`Sai2_bridge.exe` 启动后自动探测代理；图层区显示实时图层列表，
点击行 = 在 SAI2 里选中该图层并自动抓取（点行 → Ctrl+A → Ctrl+C，
剪贴板监听自动接续原有工作流）；「连接注入」按钮 = 运行 injector。

## 七、已知限制与注意事项

1. **菜单栏横向排布的行会错误地纵向步进**（主窗口组里菜单项 y 递增 31px）。
   不影响图层识别（panelGuess 评分对根窗口降权），列在已知问题。
2. **只在面板内容变化时才有新捕获**：SAI2 只重绘变化的单元格。
   注入后若图层面板从未重绘（例如刚启动、无任何操作），需点一下图层行 /
   新建图层等触发一次重绘，`layers` 才有数据。
3. **重新编译 `sai2_agent.dll` 前必须先 `eject`**，否则文件被映射无法覆盖；
   若 LoadLibraryW 曾在目标进程崩溃（远程线程 0xC0000005），需要重启目标进程
   才能解除文件占用。
4. **同一文件多次 LoadLibraryW 会使引用计数 >1**，eject 一次弹不干净，
   再 eject 一次即可。
5. 自检（selftest）使用独立管道名 `\\.\pipe\sai2agent_selftest`，
   与真 SAI2 的 agent 同时在线互不干扰。
6. 风险声明：注入与钩子仍是"官方不支持"的路线；Agent 全部代码为只读观察、
   带 SEH 级防御（无裸指针解引用，堆扫描有 VirtualQuery 页级校验），
   但不保证在所有 SAI2 版本上无副作用。使用前请保存画作。

## 八之二、透明度与图层列表修复（2026-10-07，用户实测反馈）

1. **预览黑底看不见线稿** → 预览合成到 PS 风格灰白棋盘格（EnsureBgra 按

   已改为后台线程 + WM_APP 回 UI 线程刷新，完成后把前台还给 SAI2。

## 八、SAI2 内插件入口与图层工作流（2026-10-06 增补）

### 8.1 SAI2 内浮动「插件」入口

Agent 在 SAI2 进程内创建浮窗「插件 ▾」（WS_POPUP，跟随 SAI2 主窗口右上角，
250ms 定时同步位置；类名按次加载唯一化——DLL 卸载不清理已注册窗口类，
固定类名会让第二次注入失败）。点击弹出按分组组织的原生菜单（模糊/滤镜/
调整/液化），数据来自桥的推送：

- 桥 → agent：`{"cmd":"set.plugins","items":[{"i":0,"g":"模糊","n":"高斯模糊"},...]}`
  （agent 断线重连后桥自动重推）
- 用户点选 → agent 记录待处理请求
- 桥 → agent：`{"cmd":"take.request"}`（400ms 轮询）→ 取走效果索引 →
  自动执行：应用效果 → 回写剪贴板 → 粘贴回 SAI2 →（可选）合并回原图层

### 8.2 键盘与菜单自动化的实测结论

* **SAI2 的自研输入框架不响应合成的键盘事件**——纯 VK 和 KEYEVENTF_SCANCODE
  的 SendInput Ctrl+V 都无效（按键确实到达 SAI2，但不被其加速器处理）。
  因此**一切键盘驱动一律改走 SAI2 自己的菜单**（鼠标点击菜单项）。
* 菜单项定位 = 注入代理的文字捕获（`text.recent`），前缀匹配
  （菜单项文字带助记符，如"粘贴(&P)"），取 y 最小的命中。
* **时间过滤基准必须取"打开菜单之前"的 tick**——菜单项在菜单打开瞬间渲染，
  用"当前时间-80ms"做下限会把刚渲染的菜单项全部滤掉。
* 打开菜单前先发 Esc 清掉可能残留的菜单，否则点击菜单栏变成"关闭"。
* 后台进程 SetForegroundWindow 会被前台锁拦截 → AttachThreadInput 强制前台，
  并校验 GetForegroundWindow，失败就放弃并提示。
* 查找宿主主窗口必须排除自己的浮窗（浮窗有标题且置顶，枚举序最靠前）
  并取面积最大者——否则菜单点击会落到浮窗坐标系（点在桌面上）。
* 粘贴菜单文字是"粘贴(&P)"，合并回层是"向下转写(&R)"——前缀匹配即可。

### 8.3 图层单独调整工作流（需求 3）

勾选「应用后合并回原层」后，完整闭环：

```
桥图层列表点行 → SAI2 选中该图层（点行屏幕坐标）→ Ctrl+A/C 抓取该层内容
→ 应用效果 → 回写剪贴板 → 编辑菜单粘贴（新层）→ 图层菜单「向下转写」
合并回原图层 → 调整只作用于目标层
```

### 8.4 PS 风格调整插件（com.sai2.adjust）

`调整` 分组：反相 / 去色 / 亮度对比度 / 色相饱和度 / 色阶（黑场/白场/Gamma），
全部支持选区与 Undo，桥面板参数带数值输入框（PS 风格滑杆+数值）。

## 十、抓取图层"只有上色区域大小 / 粘回去错位"的根因与修复（2026-10-15）

### 10.1 现象

注入后点「抓取选中图层」：面板里抓到的图只有图层**上色区域的包围盒**
（1920×1080 的画布抓到的是 969×593），应用后粘回 SAI2 就整体错位。

### 10.2 为什么注定错位（先厘清机制）

实测确认（`diag/clipprobe.py`）：

* SAI2 的 `Ctrl+C` **只拷贝图层不透明部分的包围盒**，透明区域被裁掉；
  即使先用 `Ctrl+A` 做出全画布选区（截图可见蚂蚁线）、等 1.2 s 再拷，
  拿到的仍然只有 969×593。剪贴板里的 `CF_DIBV5` 头为
  `headerSize=124 / BI_BITFIELDS / alphaMask=0xFF000000 / 数据起点 136`。
* 而 SAI2 的 `Ctrl+V` 按**画布 (0,0)** 对齐。

所以"抓取 → 应用 → 粘贴"要落回原位，**必须**把包围盒补边成画布尺寸并放回
原来的偏移 —— 这正是 `BridgeCore::PadToCanvas` + `AcquireCanvasContext`
（画布快照 + 多尺度模板匹配）存在的理由。

### 10.3 根因一：样本恒为空，定位**永远**失败（主因）

`BridgeApp.cpp` 的 `BuildSamples` 里：

```cpp
if (!img.GetPixel(x, y, p) || p.a < (250 << 8)) continue;   // 250<<8 = 64000
...
s.r = static_cast<uint8_t>(p.r >> 8);
```

`250 << 8`、`>> 8` 都是**按 16bit 通道**写的，但
`ImageBuffer::GetPixel` 对 **RGBA8 返回的就是 0..255**（`sdk/src/ImageBuffer.cpp`
里 `ch == 1` 分支直接取字节，不做 `Scale8To16`）。于是：

* `p.a < 64000` 对**任何**像素都成立 → `all` 恒为空 → `smp.empty()`；
* `MaskedSearch` 开头就 `if (smp.empty()) return;` → `bx` 保持 -1；
* `AcquireCanvasContext` 走到 `bestX8 < 0` → `diag = "coarse no scale with sad<=15"`
  → 返回 false → `SetCanvasContext(false,…)` → 打日志 `canvas ctx: none`
  → `WriteAppliedToClipboard` 直接写未补边的包围盒
  → **SAI2 把 969×593 贴到 (0,0)** → 偏移量正好等于包围盒原点。

这条链**与图像内容、与 SAI2 版本都无关**，每一次抓取都必然失败。
（`clipprobe.py` 打印的日志里 `canvas ctx: locate failed` / `canvas ctx: none`
反复出现，就是它。）

同类量纲错误还有 `ModalColor` 的 `p.r >> 11`（8bit 值右移 11 位恒为 0），
导致所有像素落进同一个桶，"模态色"退化成区域平均色 → 纸色判错。

**修复**：新增 `Ch8()` / `ChThresh()` 按像素格式归一，`BuildSamples` 与
`ModalColor` 全部改用它们（RGBA16 仍走 16bit 分支，向后兼容）。

### 10.4 根因二：尺度被系统性地高估

只取 `alpha>=250`（被软边"腐蚀"过的实心核心）做样本时，整块实心色在
"模板缩放到**略大于**真值"的位置仍落在视图内容内部 → SAD 形成平台 →
按"最大可通过尺度"取拐点就会**过估**。实测 0.519，真值 0.500：

* 用 0.519 反推 → 画布 1847×1038（真值 1920×1080），偏移 (332,77)
  （真值约 (352,92)）→ 即便定位"成功"，仍然错位。

**修复（Pass C 轮廓尺度精修）**：把模板按 alpha **合成到纸色**上，让
**半透明边缘与透明外框一起参与比对**（`BuildSilhouetteSamples` /
`SilhouetteSearch`），尺度一旦超过真值，外框就压到内容上、误差立刻上升。
两点关键实现细节：

1. 候选尺度的预测位置必须以**纸原点**为锚点伸缩，而不是以视图原点
   （内容相对纸的位置随尺度缩放、纸本身不动；按视图原点伸缩会让搜索窗
   覆盖不到真值，最小点被拉回初值附近 —— 只修到 0.514）；
2. 粗搜用"大窗口 + 位置步长 2"，但相邻尺度分差只有 ~0.3、与位置量化噪声
   同量级，必须**对每个尺度再做一次步长 1 的局部精修**，否则全局最小会被
   噪声拉到 0.5087。

修好后尺度评分的全局最小落在 **s=0.4983**（真值 0.5）。

### 10.5 另外两处稳健性修复

* `ForceForeground` 之前不还原最小化的窗口：SAI2 被最小化时
  `SetForegroundWindow` 不会还原它，后续合成点击全部落到
  `(-32000,-32000)` 的假坐标、画布也不会重绘。已加 `IsIconic → SW_RESTORE`
  （实测确实遇到过最小化状态）。
* 取画布快照加了**重试 + 失败原因**：`canvas.arm` 会清空快照，若期间被
  另一条链路重新 arm，`state` 说 captured 而 `save` 拿到空快照。
  现在最多重试 3 轮（重新 arm → 强制重绘 → 等新快照 → 再 save），
  并把真实原因写进 diag（`no canvas snapshot` 还是 `pipe busy` ——
  **两个面板实例抢同一个单连接同步管道**时是后者，生产上只有一个面板）。

### 10.6.2 第二个真凶：面板**自己两条线程**在抢单连接管道（2026-10-15 续）

量纲修好后，面板里抓图层仍然失败，日志变成：

```
canvas ctx: locate failed (save failed: pipe busy), fallback to plain paste
```

而 `canvas.arm` 明明刚成功过。agent 的管道日志给出了铁证（`sai2_agent_pipe_<pid>.log`）：

```
[02:58:03.504] cmd: layers            ← UI 定时器（wp==2，每 400ms）
[02:58:03.505] cmd: canvas.arm        ← 抓取线程
[02:58:03.913] cmd: take.request      ← UI 定时器
[02:58:04.320] cmd: take.request      ← UI 定时器
[02:58:04.476] cmd: canvas.state      ← 抓取线程
[02:58:04.476] cmd: canvas.save       ← 抓取线程 ← 回复被抢走，Query 返回 false
```

**根因**：agent 命名管道是**单实例同步服务**（读完一整行才回一整行），而面板里有
两条线程都在用它 —— UI 定时器（`take.request`/`ping`/`layers`）与抓取线程
（`canvas.arm/state/save`）。两者各自 `Connect` 会把服务端的"请求↔响应"配对打乱，
抓取线程发出的 `canvas.save` 拿不到自己的回复。

**第二层根因（更隐蔽）**：`AgentClient::Connect` 只把 `ERROR_PIPE_BUSY(231)` 当可重试。
但服务端每服务完一个客户端就 `DisconnectNamedPipe` → 重新 `CreateNamedPipe`，
**这中间管道名短暂不存在**，此刻 `CreateFileW` 返回 `ERROR_FILE_NOT_FOUND(2)`
（有时 `ERROR_PIPE_NOT_CONNECTED(233)`）→ 旧代码**立即返回失败**。
所以表现不是"等一会儿就好"，而是"刚发过 state、紧接着 save 就再也连不上"。

**修复三处**：

1. `AgentClient` 加**进程内互斥量**：`Connect` 取锁、`Close` 放锁，一个实例在
   生命周期内独占管道，请求/响应永远成对；
2. `Connect` 把 `ERROR_FILE_NOT_FOUND` / `ERROR_PIPE_NOT_CONNECTED` 一并视为
   "服务端暂不可用"重试到超时（BUSY 走 `WaitNamedPipe`，其余短退避 15ms）；
3. UI 定时器在 `g_cap.busy`（抓取进行中）期间**跳过 agent 轮询**，把管道让给抓取线程。

另外把两处"静默失败"改成显式记录：

* `RegisterHotKey` 的返回值以前**不检查** —— 热键被别的程序占用时注册失败，
  之后按下去什么都不发生且毫无提示。现在四个热键的注册结果都进日志。
* `BridgeCore::ApplyToClipboard` 的几条提前返回路径只写 `status_`/UI flash、
  **不进日志**，排查时连"是没执行还是提前返回"都分不清。现在都记 `apply FAILED: ...`。

**顺便修掉一个会误导人的自造问题**：`kBuildStamp` 之前用 `__DATE__/__TIME__`，
它按**翻译单元**展开，而 zig 的编译缓存会让未改动的源文件复用旧对象 ——
于是"改了 BridgeCore.cpp，BridgeApp.cpp 里的时间戳不变"，看起来像没重新编译。
已改为**直接读本 exe 的文件修改时间**，天然就是构建时刻。

### 10.6.4 残差收口：用 .sai2 文件头把画布尺寸钉死（2026-10-15 收尾）

10.6.3 之后"整体错位"已经没了，但还剩 **2~15 px** 残差，且随文档复杂度浮动。
根因很清楚：**画布尺寸是从快照推算的**（纸矩形 / 匹配出的缩放 s），而 `s` 的
估计在不同快照下会漂 1%~3.5%，偏移 `(bx-px0)/s` 就跟着漂。

**改法：不再推算，直接读。** SAI2 主窗口标题里有当前文档路径：

```
PaintTool SAI Ver.2 (64bit) Preview.2023.04.05 - Video (F:) / sai2test / align_test.sai2 (*)
```

从中解析出 `F:\sai2test\align_test.sai2`，读文件头即得**精确画布宽高**
（magic `SAI-CANVAS-TYPE0`，offset 20/24 = uint32 LE）。有了精确画布 `docW`：

```
sFile = 纸矩形宽 / docW        ← 与匹配器的 s 估计**无关**
cx0   = (bx - px0) / sFile
```

即把"尺度"从**估计量**变成**由已知基准算出的量**。为防纸矩形被选区蚂蚁线/
画笔光标啃掉一两像素而用错，加了**跨维度自洽校验**：高度方向必须独立满足
`ph/(sFile*docH) ≈ 1`（±2%）、宽度方向 `|sFile/s-1| ≤ 8%`；两条都过才采用，
否则记 `[sai2 size … rejected …]` 并退回推算。

实测（真机，同一液化流程，7 图层的最坏情况文档）：

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| `canvas ctx` | 1853x1042 / 1895x1065 / 1918x1078（每次不同） | **1920x1080（= 真值）** |
| 写进剪贴板 | 同上 | **1920x1080** |
| 落位偏移 | −4,−3 / −7,−2 | **−2,−1** |
| diag | 无标注 | `[exact 1920x1080 from .sai2, sFile=0.499479 dS=0.090944%]` |

未保存的新文档（标题里没有 .sai2）读不到尺寸，会**自动退回**原推算路径，
行为与加这个功能之前完全一致 —— 纯增益，无回归风险。

> **踩坑记录（值得单独记一笔）**：第一版把 magic 写成 `SAI2-CANV`，于是校验
> 永远失败、功能静默退回推算，现象上"完全看不出它没生效"——**与 alpha 阈值那次
> 是同一类错误：一个常量写错就让整条路静默失效**。
> 而正确的是 `SAI-CANVAS-TYPE0`，**本项目自己的 RE 成果 `SAI2-文件格式.md`
> 第 30 行早就写明**（`0x00 | char[16] | SAI-CANVAS-TYPE0 魔数`）。
> 教训：**手上有格式文档时先查文档，别靠十六进制转储肉眼比对**（当时只打印了
> 8 字节，"SAI-CANV"看着太合理，就顺手写成了 `SAI2-CANV`）。
> 为此加了 `--doc-test`，把"标题→路径→打开→读取→校验"每一步都打出来，
> 这类"静默不生效"以后 10 秒内可定位。

### 10.8 已知剩余限制（1.19 定稿时）

1. 落位残差 **1~2 px**，来自匹配到的内容位置 `bx`（±1~2 视图像素）而非尺度 ——
   尺度已由 .sai2 文件头钉死。要做 0 误差需直接读 SAI2 内存里的图层矩形（未做）。
2. 未保存的新文档没有 .sai2 文件 → 只能推算，残差回到几 px~十几 px。
3. 多图层复杂文档里，视图是所有可见图层的合成，而模板只是被复制的那一层，
   匹配位置本身会略有偏差（1~2 px 量级）。
4. agent 命名管道是**单连接**服务：同时开两个面板（或面板 + CLI 诊断）会互相抢。
   生产只有一个面板，无此问题；做诊断请先关面板。
